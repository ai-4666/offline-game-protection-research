# 오프라인 보호 연구: 예비 실험 1

이 문서는 공개 연구 결과다. 실험 코드는 공개 대상이 아니다.

## 질문

기존 방식의 단순한 구현이 REA 분석과 정상 실행 속도에 어떤 영향을 주는가? 세 버전 모두 동일한 작은 상태 전이 계산이며 실제 게임은 아니다.

## 결과

| 버전 | 로직 1회 중앙값 | 기준 대비 | REA 관찰 |
|---|---:|---:|---|
| 보호 없음 | 5.846 ns | 1.00배 | 핵심 계산을 디컴파일 |
| 수동 제어 흐름 분리 | 5.744 ns | 0.98배 | 핵심 계산이 다시 직접 노출됨 |
| 단순 가상 머신 | 107.929 ns | 18.46배 | 명령 해석기와 데이터를 읽을 수 있었음 |

```text
로직 1회 시간 중앙값 (ns, 막대 길이는 대략적인 비율)
보호 없음        5.846  ██
흐름 분리        5.744  ██
단순 VM        107.929  █████████████████████████████████████████████
```

각 값은 같은 WSL 환경에서 1천만 회 연속 호출한 실행을 무작위 순서로 7회 반복한 중앙값이다. GCC 15.2.0 `-O2`, x86-64. 같은 호출 인터페이스로 연결했으며 각 실행 결과는 동일했다. VM은 별도 컴파일을 위해 함수 가시성을 변경했다. 실제 프레임 시간이나 게임 전체 성능은 아니다. 세 버전은 경계값·무작위 입력 1,004개에서 일치했다.

REA/Ghidra 12.1.4 결과에서 제어 흐름 분리 샘플은 직접적인 계산식이 보였다. 컴파일러 최적화가 수동 제어 흐름을 없앤 것으로 보이나 각 최적화 단계를 추적한 것은 아니다. REA 재구현 시간이나 성공률 비교는 하지 않았다. 이전 단순 VM 예비 재구현은 원본 소스를 이미 본 평가자가 진행했으며 302개 입력 일치는 독립 시험이 아니다.

이 결과는 **단순 VM의 성능 비용과 단순 흐름 분리 구현의 실패 가능성**을 보여준다. 일반적인 VM 보호나 제어 흐름 난독화 전체의 효과를 평가한 결과는 아니다. 분석을 어렵게 만드는 비용이 정상 플레이에 전혀 영향을 주지 않는다는 증거도 없다.

## 다음 실험 조건

연구된 다른 방법을 추가하고, 구현 의도대로 컴파일 후에도 변환이 남는지 먼저 검증한다. 소스를 보지 못한 독립 평가, 동일한 제한 시간·도구 조건, 여러 번의 재구현 시도, 숨겨진 입력 평가가 필요하다. 게임의 프레임·로딩·메모리, 개발자의 빌드 및 디버깅 부담도 별도 측정한다.
